Lecture 5.1 · The Hook

Why Can't the Storefront Just Run SQL?

Last week you queried ClassDemo from SSMS. Imagine the website's own page code doing the same thing.

The password ships to everyone

Page code runs on the customer's computer. Anyone can open it and read the database login inside.

Anyone can type any SQL

With that login, a visitor can run UPDATE Books SET Price = 0, or worse.

Every app repeats the rules

The website, the phone app and the admin panel would each re-implement "a price can't be negative".

The fix: a counter between customer and stockroom

Customers ask at the counter ("show me book 8"); staff fetch it from the stockroom and hand it over. Customers never walk into the stockroom.

That counter is an API

An Application Programming Interface: a small program that accepts a fixed set of requests, runs the SQL itself, and returns only the answer.

This week you build that counter for the bookstore, on top of the exact database you created in Week 4.
Lecture 5.1 · The Big Picture

Three Programs, Two Languages

Storefront shows

Pages, buttons, a cart. Speaks HTTP. Knows nothing about tables.

API decides

Which requests are allowed, what is valid, which SQL to run.

Database remembers

Stores rows and enforces the constraints you wrote in Week 4.

Lecture 5.1 · HTTP

Anatomy of a Request and a Response

Every conversation with the API is one request and one response. Here a storefront adds a book.

The request

POST /books HTTP/1.1     ← method + path
Host: localhost:4000
Content-Type: application/json
                      ↑ headers
{                     ← body
  "title": "The Great Gatsby",
  "isbn":  "9780743273565",
  "price": 13.99
}

The response

HTTP/1.1 201 Created  ← status
Content-Type: application/json
                      ↑ headers
{                     ← body
  "message": "Book created successfully",
  "BookID": 10   ← from IDENTITY
}

Method

The verb: GET, POST, PUT, DELETE.

Path

The noun: which resource, /books.

Body

Data sent along, as JSON. GET has none.

Status

A 3-digit verdict: did it work?

Lecture 5.1 · REST

REST: Nouns in the URL, Verbs in the Method

You already know half of this: Create = POST = INSERT · Read = GET = SELECT · Update = PUT = UPDATE · Delete = DELETE.

MethodPathMeansSQL behind it (Week 4)
GET/booksList the booksSELECT … FROM Books
GET/books/8One book… WHERE BookID = 8
POST/booksAdd a bookINSERT INTO Books …
PUT/books/8Change book 8UPDATE Books … WHERE BookID = 8
DELETE/books/8Remove book 8DELETE FROM Books WHERE BookID = 8
GET/customers/3/ordersAli's orders… JOIN … WHERE CustomerID = 3

Resources are plural nouns

Usually one per table. An ID picks one row; a nested path follows a foreign key.

Stateless

Each request carries everything needed; the API remembers nothing between requests.

Lecture 5.1 · Quick Quiz

Call It: Which Method and Path?

Say the request out loud before the answer appears.

"Show order 13 with the books in it"

GET /orders/13 One resource by ID. The API joins OrderBooks and Books for you.

"A new author signs with us"

POST /authors The author's details travel in the JSON body. No ID in the path: the database assigns it.

"Mark order 16 as Completed"

PUT /orders/16 Body: { "status": "Completed" }.

What is wrong with GET /deleteBook?id=4?

Two things The verb is in the URL instead of the method, and a GET must never change data: browsers and search engines repeat GETs freely. It should be DELETE /books/4.

The test for any endpoint: could someone guess it from the table names alone? If yes, your API is RESTful enough.
Lecture 5.1 · Status Codes

Six Status Codes Our API Actually Sends

CodeMeaningWhen the bookstore API sends it
200 OKIt worked, here's the dataGET /books, GET /books/8, a successful PUT or DELETE
201 CreatedA new row existsPOST /books inserted a book; the reply includes its new BookID
400 Bad RequestYour data is wrongPOST without a title, a negative price, a PUT with an empty body
404 Not FoundNo such resourceGET /books/999, or a path the API doesn't have
409 ConflictIt clashes with existing dataA duplicate ISBN; deleting a book that still appears in orders
500 Server ErrorThe API itself failedDatabase offline, a bug in our code

Read the first digit

2xx: success. 4xx: the client must change the request. 5xx: the server must be fixed; retrying might work.

The "everything is 200" mistake

Replying 200 {"error": "not found"} forces every app to read the text to learn it failed. The status code exists so they don't have to.

Lecture 5.1 · async & await

Waiting for the Database Without Freezing

A query takes milliseconds to seconds. Node must not stop serving every other customer while it waits.

Forget await: wrong answer

const result = pool.request()
  .query("SELECT * FROM Books");
res.json(result.recordset);

The query has only started. result is a Promise, an IOU, so recordset is undefined and the client gets an empty reply.

With await: the real rows

const result = await pool.request()
  .query("SELECT * FROM Books");
res.json(result.recordset);

await pauses this request until SQL Server answers. Meanwhile Node keeps handling other requests.

The rule

Any function that uses await must be declared async. That's why every controller begins export const listBooks = async (req, res) =>.

The analogy

A waiter takes your order to the kitchen and serves other tables while it cooks. They don't stand at the kitchen door until your food is ready.

Lecture 5.1 · Lab · Step 5 of 6

Serve Books, and Say 404 When There Isn't One

No database yet: three real bookstore rows in a JavaScript array. Add this above app.listen, then stop (Ctrl + C) and restart the server.

const books = [
  { BookID: 1, Title: "1984", Price: 12.99 },
  { BookID: 2, Title: "Animal Farm", Price: 9.99 },
  { BookID: 8, Title: "Tales of the Unknown", Price: 18.50 }
];

app.get("/books", (req, res) => {
  res.json(books);
});

app.get("/books/:id", (req, res) => {
  const id = parseInt(req.params.id);
  const book = books.find(b => b.BookID === id);
  if (!book) {
    return res.status(404).json({ error: "Book not found" });
  }
  res.json(book);
});

:id is a placeholder

For /books/8, Express puts "8" in req.params.id. It arrives as text, so parseInt turns it into the number 8.

return stops the function

Without it, the code would go on to send a second reply, and Express would throw an error.

Lecture 5.2 · Setup

Give the API Its Own Database Login

SSMS signed you in with Windows. The Node driver signs in with a SQL Server username and password, so SQL Server needs three switches.

1 · Allow SQL logins

SSMS: right-click the server → Properties → Security → SQL Server and Windows Authentication mode. Then restart the SQL Server service.

2 · Turn on TCP/IP

SQL Server Configuration Manager → Network Configuration → Protocols → TCP/IP: Enabled. For SQLEXPRESS, also start the SQL Server Browser service.

3 · Create the login

Run the script on the right in SSMS, choosing your own password. Put the same name and password in .env.

CREATE LOGIN bookstore_app
  WITH PASSWORD = N'pick-your-own-Strong-1';
GO
USE ClassDemo;
CREATE USER bookstore_app FOR LOGIN bookstore_app;
ALTER ROLE db_datareader ADD MEMBER bookstore_app;
ALTER ROLE db_datawriter ADD MEMBER bookstore_app;

Least privilege

This login can read and write rows, but it cannot DROP a table or create logins. If the API is ever hacked, the damage stops at the data it was already allowed to touch.

Lecture 5.2 · Security

Never Glue User Input Into SQL

Everything in req.params, req.query and req.body is typed by a stranger.

Dangerous: string building

pool.request().query(
  `SELECT * FROM Books
   WHERE BookID = ${req.params.id}`);

A visitor requests /books/1; DELETE FROM Payments and SQL Server receives:

SELECT * FROM Books WHERE BookID = 1; DELETE FROM Payments

Two statements. Both run. Every payment is gone.

Safe: a typed parameter

pool.request()
  .input("bookId", sql.Int, bookId)
  .query(`SELECT * FROM Books
          WHERE BookID = @bookId`);

The SQL text and the value travel separately. SQL Server never reads the value as code; "1; DELETE…" is simply not a valid Int and is rejected.

This is called SQL injection, and it has been near the top of every web-security risk list for twenty years. The rule is absolute: values go in .input(), never inside the query string. Every query in bookstore-api follows it.

Lecture 5.2 · PUT & DELETE

Update and Delete: Translate the Database's "No"

SQL error numbers mean nothing to a storefront. The API turns them into a status code and one sentence of JSON.

PUT /books/4 changes only what you send

UPDATE Books

Lecture 5.2 · Errors

Three Safety Nets in server.js and the Controllers

1 · try / catch in every controller

try { … }
catch (error) {
  console.error(error);
  res.status(500).json({
    error: "Failed to fetch" });
}

Without it, a failed query leaves the request hanging until the client times out.

2 · A 404 for unknown paths

app.use("*", (req, res) =>
  res.status(404).json({
    error: "Endpoint not found"
  }));

Registered after every router, so it only catches what nothing else matched.

3 · A last-resort handler

app.use((err, req, res, next) =>
  res.status(500).json({
    error: "Internal server error"
  }));

Four parameters tell Express this function handles errors.

Log the details, send the summary. The full error (table names, SQL text) goes to console.error on the server. The client gets one plain sentence. Error details are a map of your database for an attacker.
Order matters here too: routes/orders.js lists /stats before /:id. Swap them and GET /orders/stats is treated as an order whose ID is "stats".

Week 5 · Wrap-Up

What You Now Know

  • An API sits between storefront and database: it holds the password, the SQL and the rules.
  • HTTP is request and response: method, path, body, status code. JSON is the shape of the data.
  • REST maps nouns to paths and verbs to methods, which map one-to-one onto INSERT, SELECT, UPDATE, DELETE.
  • Express routes each request to a controller; await waits for SQL Server without freezing.
  • Safe by default: parameters against injection, secrets in .env, SQL errors translated into 400, 404, 409.
