Lecture 4.1 · Setup

The Toolbox: Engine, Window, Database

SQL Server

The engine. A program running in the background that stores the data and executes your SQL. It has no screen of its own.

SSMS

The window. SQL Server Management Studio is where you type queries and see results. It only talks to the engine.

ClassDemo

The database. One engine holds many databases; ours is called ClassDemo and holds the 7 bookstore tables.

First connection

  • Server name: localhost or localhost\SQLEXPRESS
  • Authentication: Windows Authentication
  • Tick Trust server certificate, then Connect
  • New Query, type, press F5 to run
CREATE DATABASE ClassDemo;
GO
USE ClassDemo;
GO
SELECT DB_NAME();  -- should answer: ClassDemo
The number one beginner mistake: running your script in master. Before every F5, read the database dropdown in the toolbar. It must say ClassDemo.

Lecture 4.1 · CREATE TABLE

Your First Table, Line by Line

CREATE TABLE Books (
  BookID      INT IDENTITY(1,1) PRIMARY KEY,   -- invented key: the database numbers rows 1, 2, 3…
  Title       NVARCHAR(255) NOT NULL,          -- required: no book without a title
  ISBN        NVARCHAR(20)  NOT NULL UNIQUE,   -- required, and no two books may share one
  Genre       NVARCHAR(100) NULL,              -- optional
  PublishDate DATE          NULL,
  Description NVARCHAR(MAX) NULL,              -- long text, also optional
  Price       DECIMAL(10,2) NOT NULL,          -- money: exact to the cent, never FLOAT
  Stock       INT           DEFAULT 0,         -- say nothing and it is 0
  CreatedAt   DATETIME      DEFAULT GETDATE()  -- stamps "now" by itself
);

The shape of every CREATE TABLE

Name, then a comma-separated list in parentheses. Each line is column name · type · rules. No comma after the last one.

Run it, then look

F5, then refresh Tables in Object Explorer. dbo.Books appears: empty, but already guarding its rules.

Lecture 4.1 · Data Types

Six Data Types Cover an Entire Store

TypeUse it forIn our schema
INTIDs, counts, quantitiesBookID, Stock, Quantity
DECIMAL(10,2)MoneyPrice, UnitPrice, TotalAmount
NVARCHAR(n)Short text, up to n charactersTitle (255), Email (255), Status (50)
NVARCHAR(MAX)Long textDescription, Bio
DATE / DATETIMEA day / a day and timePublishDate / OrderDate, CreatedAt
BITYes or no (1 or 0)Author_Book.isMain

Why not FLOAT for money?

FLOAT stores approximations, so sums drift by fractions of a cent. DECIMAL(10,2) stores exactly two decimals, up to 99,999,999.99.

Why NVARCHAR and not VARCHAR?

The N means Unicode. A customer named علي or Zoé is stored correctly. Write text values as N'…'.

Lecture 4.1 · Foreign Keys

The Relationship Line Becomes a Constraint

CREATE TABLE Orders (
  OrderID     INT IDENTITY(1,1) PRIMARY KEY,
  CustomerID  INT           NOT NULL,
  OrderDate   DATETIME      DEFAULT GETDATE(),
  TotalAmount DECIMAL(10,2) NOT NULL,
  Status      NVARCHAR(50)  DEFAULT 'Pending',

  CONSTRAINT FK_Orders_Customers
    FOREIGN KEY (CustomerID)
    REFERENCES Customers(CustomerID)
);

Read it aloud

"The CustomerID in Orders must be a CustomerID that exists in Customers."

What it guarantees

No order for a customer who does not exist. No deleting a customer who still has orders.

Give it a name

FK_Child_Parent. The name appears in error messages, so a good one tells you what went wrong.

Same rule as the diagram: the foreign key sits on the "many" side. Orders carries CustomerID; Customers knows nothing about orders. The two columns must have the same data type.
Lecture 4.1 · Foreign Keys

A Bridge Table Is Just Two Foreign Keys

CREATE TABLE OrderBooks (
  OrderBookID INT IDENTITY(1,1) PRIMARY KEY,
  OrderID     INT           NOT NULL,
  BookID      INT           NOT NULL,
  Quantity    INT           NOT NULL
              CHECK (Quantity > 0),
  UnitPrice   DECIMAL(10,2) NOT NULL,

  CONSTRAINT FK_OrderBooks_Orders
    FOREIGN KEY (OrderID)
    REFERENCES Orders(OrderID),
  CONSTRAINT FK_OrderBooks_Books
    FOREIGN KEY (BookID)
    REFERENCES Books(BookID)
);

Facts about the pair

Quantity and UnitPrice belong to "this book in this order", so they live here. CHECK refuses a line with zero books.

Two 1:N links

One foreign key to Orders, one to Books. That is the whole many-to-many, exactly as you drew it.

The other bridge

Author_Book follows the same pattern: BookId, AuthorId, and its own fact, isMain BIT.

Lecture 4.1 · Creation Order

Parents First, Children After

A table can only reference a table that already exists. So the order of your script matters.

Msg 1767 · Foreign key 'FK_Orders_Customers' references invalid table 'Customers'.
Msg 1750 · Could not create constraint or index. See previous errors.
That is what you see if Orders runs before Customers. Arrows point from child to parent: create along the levels, drop in reverse. Our sqlSchema.sql uses the other valid approach: all tables first, then the foreign keys added at the end with ALTER TABLE.
Lecture 4.1 · Quick Quiz

Spot the Bugs: a Reviews Table

A teammate wants customers to rate books from 1 to 5. Find four problems before they appear.

CREATE TABLE Reviews (
  ReviewID   INT,
  BookID     INT,
  CustomerID INT
    REFERENCES Customer(CustomerID),
  Rating     FLOAT,
  Comment    VARCHAR(50),
  CreatedAt  DATETIME
);

1 · No primary key

ReviewID is a plain INT. It needs IDENTITY(1,1) PRIMARY KEY.

2 · BookID points nowhere

No foreign key and no NOT NULL: a review of a book that does not exist.

3 · Wrong table name

The table is Customers. This script stops with Msg 1767.

4 · Rating can be 3.7 or 900

Use INT with CHECK (Rating BETWEEN 1 AND 5).

Bonus points: VARCHAR(50) cuts comments at 50 characters and breaks on Arabic text, and CreatedAt has no DEFAULT GETDATE(). Only bug 3 stops the script. The other five are accepted silently, which makes them the dangerous ones.
Lecture 4.1 · Changing Your Mind

ALTER and DROP: When the Design Changes

Add a column to a live table

ALTER TABLE Books
  ADD CoverUrl NVARCHAR(500) NULL;

Existing rows get NULL. A new NOT NULL column needs a DEFAULT, or SQL Server refuses.

Remove a table completely

DROP TABLE Author_Book;  -- child first
DROP TABLE Authors;      -- then parent

The table and every row in it are gone. There is no undo and no recycle bin.

Running a script twice

Msg 2714 · There is already an object named 'Books' in the database.

CREATE TABLE is not repeatable. Drop the table first, or start from an empty database.

Dropping a parent that is still referenced

Msg 3726 · Could not drop object 'Orders' because it is referenced by a FOREIGN KEY constraint.

Foreign keys protect tables as well as rows.

Last week's promise, kept: "an hour of care saves a week of ALTER TABLE." Adding a column is easy. Splitting a table that already holds real orders is a project.

Lecture 4.2 · INSERT

INSERT: One Sentence, One Row

INSERT INTO Books (Title, ISBN, Genre, Price, Stock)
VALUES (N'Dune', N'9780441013593', N'Science Fiction', 17.99, 25);
BookIDTitleISBNGenrePriceStockPublishDateCreatedAt
9Dune9780441013593Science Fiction17.9925NULLtoday, now

You never typed BookID

IDENTITY assigned 9, the next number after the 8 seed books. CreatedAt came from its DEFAULT.

Columns and values line up

First value goes to the first column listed, and so on. Text in single quotes, numbers without.

An apostrophe inside text

Double it: N'Sorcerer''s Stone'. A backslash does not work in SQL Server.

Always list the columns. INSERT INTO Books VALUES (…) works until someone adds a column, and then every insert in your application breaks.
Lecture 4.2 · The Schema in Motion

One Order, Typed by Hand

Last week you watched an order flow through 5 tables. Now you write it. Ali Hassan (CustomerID 3) buys one 1984 and two Animal Farm.

1 · Orders (+1 row)

INSERT INTO Orders (CustomerID, TotalAmount)
VALUES (3, 32.97);
SELECT SCOPE_IDENTITY();  -- the new OrderID: 16

2 · OrderBooks (+2 rows)

INSERT INTO OrderBooks
  (OrderID, BookID, Quantity, UnitPrice)
VALUES (16, 1, 1, 12.99),
       (16, 2, 2, 9.99);

3 · Books (stock updated)

UPDATE Books SET Stock = Stock - 1
WHERE  BookID = 1;
UPDATE Books SET Stock = Stock - 2
WHERE  BookID = 2;

4 · Payments (+1 row)

INSERT INTO Payments
  (OrderID, Amount, PaymentMethod,
   TransactionReference)
VALUES (16, 32.97, N'Credit Card', N'TXN3016');
Same rule as creating tables: the parent row first. The order must exist before its lines and its payment can point at it. If your SCOPE_IDENTITY() is not 16, use your own number in steps 2 and 4.
Lecture 4.2 · Constraints at Work

The Database Says No

Three statements that look reasonable. Predict what happens before the answer appears.

A second copy of 1984

INSERT INTO Books
  (Title, ISBN, Price)
VALUES (N'1984 (new)',
  N'9780451524935', 10.99);
Msg 2627 · Violation of UNIQUE KEY constraint. Cannot insert duplicate key in object 'dbo.Books'. The duplicate key value is (9780451524935).

An order for nobody

INSERT INTO Orders
  (CustomerID, TotalAmount)
VALUES (999, 20.00);
Msg 547 · The INSERT statement conflicted with the FOREIGN KEY constraint "FK_Orders_Customers" … table "dbo.Customers", column 'CustomerID'.

Zero copies of a book

INSERT INTO OrderBooks
  (OrderID, BookID,
   Quantity, UnitPrice)
VALUES (16, 3, 0, 14.99);
Msg 547 · The INSERT statement conflicted with the CHECK constraint … table "dbo.OrderBooks", column 'Quantity'.
Three refusals, zero rows of bad data. Each message names the constraint, the table and the column. This is the "database defends itself" idea from Week 3, now running.
A side effect you will notice: a refused insert still uses up an ID. Your next order may be 18, not 17. Gaps in IDs are normal; never rely on IDs being consecutive.
Lecture 4.2 · UPDATE & DELETE

WHERE Is Your Seatbelt

With WHERE: one order changes

UPDATE Orders
SET    Status = N'Completed'
WHERE  OrderID = 16;
(1 row affected)

Without WHERE: every order changes

UPDATE Orders
SET    Status = N'Completed';
(16 rows affected) — no warning, no undo

DELETE obeys foreign keys too

DELETE FROM Customers
WHERE  CustomerID = 3;
Msg 547 · The DELETE statement conflicted with the REFERENCE constraint "FK_Orders_Customers" … table "dbo.Orders".

The professional habit

  • Write the WHERE as a SELECT first
  • Check that the rows shown are the ones you mean
  • Then change SELECT to UPDATE or DELETE
  • Read "rows affected" every single time
Why stores rarely delete: Ali has orders, so his row cannot go, and you would not want it to; the sales history needs him. Real stores mark a customer inactive with an UPDATE.
Lecture 4.2 · SELECT

SELECT: Asking the Database a Question

"Which books cost less than $13, cheapest first?"

SELECT   Title, Genre, Price   -- which columns
FROM     Books                 -- which table
WHERE    Price < 13            -- which rows
ORDER BY Price;                -- in what order
TitleGenrePrice
Animal FarmPolitical Satire9.99
Murder on the Orient ExpressMystery11.99
1984Dystopian12.99

SELECT *

Every column. Fine for a quick look in SSMS; in application code, name the columns you need.

More filters

Genre = N'Horror'
Title LIKE N'%Potter%'
Price BETWEEN 10 AND 15

Only the first few

SELECT TOP (3) … with an ORDER BY gives you a top-3 list.

SELECT never changes anything. You cannot break the database by asking it questions, so experiment freely.
Lecture 4.2 · JOIN

JOIN: Follow the Foreign Key

Orders stores only CustomerID 3. To see a name next to each order, walk the relationship line.

SELECT   o.OrderID, c.FirstName, c.LastName, o.TotalAmount, o.Status
FROM     Orders o
JOIN     Customers c ON o.CustomerID = c.CustomerID   -- FK on the left, PK on the right
WHERE    c.Country = N'Lebanon'
ORDER BY o.OrderID;
OrderIDFirstNameLastNameTotalAmountStatus
3AliHassan31.98Completed
13AliHassan148.92Pending
16AliHassan32.97Completed

The ON clause is the relationship

It is the line from your ERD written as a condition: this order's CustomerID equals that customer's CustomerID.

o and c are nicknames

Aliases save typing and say which table a column comes from. Both tables have a CustomerID, so you must say which one.

Order 16 is the one you typed. Normalization stored Ali's name once; JOIN puts it back next to every order whenever you ask.
Lecture 4.2 · JOIN

Across a Bridge: Two JOINs

"Who wrote Tales of the Unknown?" Books and Authors are many-to-many, so the path goes through Author_Book.

SELECT b.Title,
       a.FirstName + N' ' + a.LastName AS Author,
       ab.isMain
FROM   Books b
JOIN   Author_Book ab ON b.BookID = ab.BookId
JOIN   Authors a      ON ab.AuthorId = a.AuthorID
WHERE  b.Title = N'Tales of the Unknown'
ORDER BY ab.isMain DESC;
TitleAuthorisMain
Tales of the UnknownAgatha Christie1
Tales of the UnknownGeorge Orwell0
Tales of the UnknownJ.K. Rowling0

Count the hops

Books → Author_Book → Authors. Two relationship lines on the ERD, two JOINs in the query.

One book, three rows. A JOIN returns one row per matching pair, so a book with three authors appears three times. Remember this in Week 5: the API has to fold these rows back into one book with a list of authors.
Lecture 4.2 · A First Business Question

"What Are Our Three Best Sellers?"

SELECT TOP (3)
       b.Title,
       SUM(ob.Quantity)                AS UnitsSold,
       SUM(ob.Quantity * ob.UnitPrice) AS Revenue
FROM   OrderBooks ob
JOIN   Books b ON ob.BookID = b.BookID
GROUP BY b.Title
ORDER BY Revenue DESC;
TitleUnitsSoldRevenue
The Da Vinci Code22307.78
The Shining18287.82
Harry Potter and the Sorcerer's Stone18269.82

GROUP BY makes piles

All order lines for the same title go into one pile; SUM adds up each pile. One row comes out per book, however many lines went in.

Why UnitPrice and not Books.Price

Revenue is what customers actually paid on the day. That is why the price was copied onto the order line.

The answer lives in the bridge table. OrderBooks looked like plumbing on the ERD; it is where every sales question gets answered. Same units for two books, different revenue: price matters.
Lecture 4.2 · Quick Quiz

Call It: Which SQL Does the Job?

Name the statement and the key clause before the answer appears.

"Raise the price of The Shining to 16.99"

UPDATE + WHERE SET Price = 16.99 WHERE BookID = 4. Old order lines keep 15.99 in UnitPrice.

"List every customer in the USA"

SELECT + WHERE One table, one filter: WHERE Country = N'USA'. No JOIN needed.

"Show each payment with the customer's email"

2 JOINs Payments → Orders → Customers. Payments has no CustomerID; you reach it through the order.

"A new author signs with us"

INSERT One row in Authors. Linking the author to a book is a second INSERT, into Author_Book.

The method for any question: find the tables that hold the facts, trace the path between them on the ERD, and write one JOIN per line you cross.

Lecture 4.2 · Back to Your Project

From Your ERD to Your Script

Your Week 3 diagram already contains most of the SQL. Five steps turn it into a database.

  • 1 · Export from dbdiagram.io: Export → SQL Server. You get a first draft of every CREATE TABLE.
  • 2 · Fix the types: NVARCHAR for text, DECIMAL(10,2) for money, IDENTITY(1,1) on every primary key.
  • 3 · Add the guardrails the diagram could not show: NOT NULL, UNIQUE, DEFAULT, CHECK.
  • 4 · Order it: parents first, children after, and name every foreign key FK_Child_Parent.
  • 5 · Seed it: at least 5 rows per table, inserted in the same parent-first order.
The test that matters: create an empty database, run your script once from top to bottom, and get zero red messages. If it passes that, anyone on your team can rebuild the database in ten seconds.

Week 4 · Wrap-Up

What You Now Know

  • CREATE TABLE turns each ERD box into a table: column, type, rules.
  • Constraints (PRIMARY KEY, NOT NULL, UNIQUE, DEFAULT, CHECK, FOREIGN KEY) make the database refuse bad data by itself.
  • Parents first, for creating tables and for inserting rows; the reverse for dropping.
  • INSERT, UPDATE, DELETE change data, and WHERE decides how much of it.
  • SELECT with JOIN walks the relationship lines; one JOIN per line, two to cross a bridge.
